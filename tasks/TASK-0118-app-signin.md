# TASK-0118: installed app browser sign-in claims

- Scope: takos-storage Phase 7, coordinated with the Takosumi app ownership migration. Takosumi owns claim issuance; this repository owns browser sessions and Drive access. No other repository is edited here.
- Authorization: match `takosumi.capsule_id` to configured `APP_CAPSULE_ID`; accept only the shared `AppRole` values `owner`/`member`. A matching Capsule authorizes the app identity; an absent app_role permits ordinary sign-in but does not grant private Drive access. Private data requests revalidate UserInfo for the same subject/exact Capsule and current owner/member role or exact-capsule matching legacy Workspace membership while app_role is absent; retained tokens are encrypted in context-bound AES-GCM cookies. HMAC app-role cookies cannot grant data access. A pre-deploy session cookie without a Capsule is cleared and returns 401 `reauthentication_required` on `/api/drive` and `/api/auth/me`; a current matching-Capsule user without membership still receives 403. UserInfo has a ten-second deadline; UserInfo 401 clears the cookie and returns 401 reauthentication_required for the console login redirect; other unavailable authority denies private data (no refresh flow added). There is no separate Storage management surface; `/api/auth/me` omits cached role snapshots so they cannot appear to be current management authority. Foreign or malformed app claims cannot use Workspace compatibility.
- Compatibility: existing Workspace-only claims and session cookies retain the configured `APP_WORKSPACE_ID` membership rule and never gain an app role. When APP_CAPSULE_ID is configured, missing capsule claims deny admission. Without that configuration, capsule claims are ignored and legacy Workspace admission remains. Interface OAuth requires the configured exact Capsule, or the configured exact Workspace on legacy installs. With a configured Capsule, Workspace evidence is optional even when legacy configuration remains; a present Workspace claim is shape-checked and matched to any configured legacy Workspace. Current audience, permission, binding and revision checks remain required.
- Deployment order: update consumer apps first; deploy the Takosumi Accounts open sign-in writer B (#657) last. Until an existing self-host install is updated with Capsule context, it continues to rely on `APP_WORKSPACE_ID` membership.
- Runtime: both modules bind `APP_CAPSULE_ID` and optional legacy `APP_WORKSPACE_ID` independently from optional `takosumi_capsule_id`/`takosumi_workspace_id` variables. The portable module uses non-secret `vars_json`; the v2.5 manifest declares `capsule_id` and deprecated compatibility `workspace_id` context sources, which Takosumi validates and compiles into its service-owned InstallConfig mapping. The OIDC sensitive runtime recipe stays unchanged. The portable module validates ids and requires Capsule or legacy Workspace context, preserving existing installs before the v2.5 mapping upgrade; no inferred id or unsupported manifest field is added. No live InstallConfig was changed by this source-only task.
